# 登録宣言と受付記録の段階移行

新しい施設登録・掲載申込画面は、既存の利用規約・プライバシーポリシーへの同意と、必要な許認可の表明を改めて確認する。入力・写真のバックアップから同意や表明を復元しない。一般利用者のアカウント作成は許認可の表明を要求せず、明示同意と Google 開始前のチェックを行う。ブラウザーからの Supabase Auth 登録・外部プロバイダー全入口に新しい DB 同意義務を加えたものではない。

施設登録の新 producer は outer `consent` envelope を送出する。API は提供された宣言の真偽を検証し、新受付は `salons` の別列へ規約内容版の SHA256、サーバー時刻、許認可の表明を保存する。SHA256 は規約・プライバシー・共有退会案内のコード内容を識別する版であり、新しい法的効力発生日を意味しない。表明は提供者の宣言であり、実際の許認可を確認済みと認定する記録ではない。保存期間・本文・業務 canonical/HMAC は変更しない。

M8 は列と新 service-only wrapper を追加する。V2 の受付・intent・通知予約・宣言保存は同一 transaction で完了し、宣言保存の失敗もすべて rollback する。元の業務 HMAC による比較と、元の receipt の再取得を維持する。受付済みの replay では同意版や時刻を上書きせず、旧受付の NULL を新同意に変更しない。

旧開いた V1 フォームと既発行 V2 intent を維持するため、宣言を省略した従来 consumer は grace として従来経路で処理する。記録は NULL、未確認のまま保持する。新 producer の宣言検証・記録が完成しても、すべての匿名登録入口で同意の送出を強制したとは認定しない。

明示的な不正宣言を受けた V2 は有効な proof と元の内容を照合して受付状況を確認する。400 応答だけで以前の要求が未送信・未受付だったと断定せず、結果不明の入力 fence を保持する。元の結果を確認するか、元と同一の要求を照合した再実行に限る。異なる入力や新しい intent への自動転換は行わない。

適用順は M8 の追加 DB 変更を先に検証してから新 producer/API を配信する。旧 V1/V2 の拒否へ進める formal cutover は、旧匿名 Storage 停止の影響を本人が選択し、入力を保持した移行手順を決めた後に行う。その時点で consent の省略 grace の終了も明示する。旧フォームの停止を本修正に隠して追加しない。
