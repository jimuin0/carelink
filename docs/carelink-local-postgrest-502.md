# ローカルPostgRESTのHEAD接続とCIの502

2026-10-16。PR #709の初回head `73f6da244c086599299ce26ec892ed7554a81fb5` のCI `38842127059` は、Mobile Safariの掲載申込復旧で363 expected / 1 flaky / unexpected 0となり失敗した。再試行成功を根因解消とは扱わない。

初回テスト開始02:57:27 UTC、02:57:32 UTCに復旧一覧RPCが固定診断 `unclassified / HTTP 502` を記録し、受付行の表示待ちが失敗した。認証確認不能や不正な一覧スキーマの診断はなかった。ログ本文とスタックの重複を別々のRPC失敗とは数えない。

## 通信で確認した不具合

CareLinkのローカルAPIはPostgREST v14.12だった。同じローカルDBに対するHEADのみの比較で、既存APIは3/3回とも `Connection: close` もContent-Lengthも返さず接続を閉じ、同じ接続の次の要求を受け取れなかった。比較用のv14.15は3/3回とも `Connection: close` を通知した。

[Supabase CLIの公式Issue #6674](https://github.com/supabase/cli/issues/6674)には、古いPostgRESTがHEAD接続を黙って閉じ、Kongがその接続を再利用した際にPOST/PATCHを502にする不具合と、v14.15以降の修正が記録されている。今回のHTTP 502と通信不具合はこの原因に整合する。失敗したCIのKong内部ログ自体は取得できていないため、個別の接続IDまで同定したとはしない。

既存のDB・API・Gatewayは停止/再構成していない。比較用APIコンテナだけ作成後に削除した。行・認証情報・IP・ヘッダー全文は記録しない。

## 修正と検証

- SQL文分割器を検証済みのCLI 2.104.0は維持し、CI開始前に `supabase/.temp/rest-version` へv14.15を固定する。変更は隔離ローカルAPIのイメージだけ。
- fresh-apply後、実際のHEAD応答が切断を通知するか、同じ接続で次のHEADを処理できることを確認する。HTTP障害を正常として通さない。
- 実ローカルsocketを使う4ケースで、黙った切断の拒否・切断通知の許可・継続接続の確認・503の拒否を検証する。公式ECR/GHCRのv14.15だけを許可し、別バージョン・別レジストリ・別プロジェクト・公開IP・任意の接続先指定は拒否する。Dockerから取得する情報も名前/稼働状態/イメージ/ローカルネットワークだけに限定する。
- 既存のfresh-apply、型生成、API契約、E2E全件とflaky失敗ゲートを維持する。アプリの再送、テストの再試行/待ち時間、skipは変更しない。

ホストされた本番Supabaseや業務データは変更しない。PR #700の遷移待ち、#704のHTTP状態未採取の一覧失敗、その他の過去500を同じ根因で解消したとは認定しない。最新CIの成否・本番反映は既存再開台帳で別に管理する。

初回の通信ゲート実行 `38845081224` は、CIが使用する公式GHCRミラーを検査側が考慮せず、通信検査前に停止した。これは検査実装の不足として保持する。公式2ミラーの同じ修正版だけを許可するよう修正し、通信の合否条件は維持した。
