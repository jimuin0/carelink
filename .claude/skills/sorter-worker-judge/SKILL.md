# sorter → worker×8 → judge

**「一番賢いモデルに全部やらせる」のではなく、一番賢いモデルには一番重要な判断（最終レビュー）だけをやらせる。** 大量の独立したタスクがあるとき、Haiku・Sonnet・Opus を「仕分け・実働・最終判定」の3役に分けて動かし、コストと速度を最適化しつつ品質は「作った本人が採点しない」構造で担保する。

```
Haiku sorter (仕分け)
  → 大量タスクをグループ分け＋作業指示書(brief)を作成
Sonnet worker ×最大8並列 (実働)
  → グループごとに実装
Opus judge (最終判定)
  → 完成物だけを独立検証 → 承認 or 差し戻し(理由付き)
       └── 差し戻されたら worker が修正 → 再度 judge (最大2〜3周)
```

## いつ使うか

**向いている**: 独立性の高い小〜中タスクが多数ある。例:
- 「N個のファイルに同じような修正を入れたい」
- 「洗い出したバグを全部直したい」
- 「各ルートハンドラにテストを追加したい」
- 「複数の小さい独立した機能を並列で実装したい」

**向いていない**: タスクが1〜2個しかない、または全工程を通して高度な設計判断が必要（アーキテクチャ変更・複数タスクが密結合）。この場合は普通に自分で実装するか、より重い専用スキル（例: `feature-factory`）を使う。無理に本スキルへ押し込まない。

## なぜこれで安く・速くなるか

- **モデルは役割に対して過剰なほど無駄**。分類・グルーピングのような軽い判断に一番高価なモデルを使う理由はない。Haiku で十分な精度が出る作業をそこに寄せる。
- **実装は並列化できる**。8並列の Sonnet worker はそれぞれ独立したタスクを同時にこなすので、直列で1体のモデルにやらせるより速い。
- **最終判定だけ最も賢いモデルに集約する**。Opus は「完成物を読んで基準を満たしているか」だけを見る。判断の総量を絞ることで、賢いモデルのコストを「本当に賢さが要る箇所」に集中させられる。
- **自己採点をしない**。実装した本人（Sonnet worker）に「完璧です」と言わせるのではなく、別モデル（Opus）が独立に検証する。人間の組織と同じで、作る係と検査する係を分けることで見落としが減る。

数値（コスト削減率・処理速度倍率）はタスクの性質・分量・モデル料金によって変わるため、このスキル自体には固定の数字を書かない。実測したい場合は同じタスクをこのパイプライン有無で走らせ、実際のトークン数・所要時間を比較する。

## 実行手順

このパターンは [`Workflow`](workflow tool) を使う。**このスキルをユーザーが名指しで呼んだこと自体が、Workflow ツールが要求する「明示的なマルチエージェント opt-in」に該当する**（ツール説明の「ユーザーがスキル/スラッシュコマンドを呼び、その指示が Workflow を呼ぶよう書かれている」に合致）。改めて確認を取る必要はない。

### Step 1: タスクリストを確定する

Workflow スクリプトは `args.tasks`（文字列の配列）を受け取る。ユーザーが既に箇条書きでタスクを列挙していればそのまま使う。「全ファイルに〜」のような1つの大きい指示しか無い場合は、**Glob/Grep 等で実際に対象を列挙してから**具体的なタスク文字列の配列にする（何が対象か推測で決めない）。

タスク件数の見積もりに応じて `maxWorkers`（既定8）・`maxRetries`（既定2＝最大3回試行）を決める。タスクが3件しかないのに8並列に水増しする必要はない — sorter が作るグループ数がそのまま並列度になる。

### Step 2: Workflow スクリプトを読み、`args` を埋めて実行する

`scripts/workflow.js` がこのパイプラインの本体（sort → work → judge → 差し戻しループ）。**このファイルを直接編集しない** — プロジェクト固有の値をハードコードしたくなったら `args` 経由で渡す（`context` フィールドに対象プロジェクトの制約・CLAUDE.md の要点などを積める）。

```
1. Read scripts/workflow.js の内容を取得
2. Workflow({
     script: <上記の内容そのもの>,
     args: {
       tasks: ["タスク1の説明", "タスク2の説明", ...],
       context: "対象プロジェクトの制約・注意点（任意）",
       maxWorkers: 8,     // 省略可
       maxRetries: 2,     // 省略可
     },
   })
```

### Step 3: 結果を報告する

Workflow の戻り値は `{ approved, failed, escalated_by_sorter, summary }`。

- `escalated_by_sorter`: sorter が「自動処理には危険/曖昧すぎる」と判断し、そもそもワーカーに渡さなかったタスク。**必ず人間に報告し、対応方針を確認する**（黙って無視しない）。
- `failed`: judge が既定回数の差し戻しでも承認できなかったグループ。**必ず人間に報告し、最後の却下理由を添える**（諦めて放置しない）。
- `approved`: judge が独立検証の上で承認したグループ。

## 守るべきガードレール

- **このスキルはコード変更を作るところまで**。commit・push・PR作成・マージ・デプロイの可否は、対象プロジェクトの既存ルール（例: soel の CLAUDE.md にある「本番変更は明示 GO 後のみ」「高リスク変更は独立検証してからマージ」）が引き続き適用される。Opus judge は追加の品質ゲートであって、そのプロジェクトの人間承認ゲートの代わりにはならない。
- **judge は worker の自己申告を根拠にしない**。`scripts/workflow.js` の judge プロンプトは「自分で確認しろ、報告を鵜呑みにするな」と明示している。ここを弱めない。
- **共有ファイル・共有リソースに触れるグループは worktree 隔離する**。sorter の出力 `touches_shared_files` を見て worker 呼び出しに `isolation: 'worktree'` を付ける（`scripts/workflow.js` は既にそうなっている）。対象プロジェクトに「越境影響のある共有識別子」の定義があるなら（soel の CLAUDE.md 参照）、sorter への `context` にその一覧を渡し、該当タスクは `escalate` に回すよう促す。
- **差し戻しループには上限がある**（既定2回の差し戻し＝最大3回試行）。無限にリトライさせない。上限に達したら人間へ。

## カスタマイズポイント

`scripts/workflow.js` を読んでから、必要なら `args` で以下を調整する（スクリプト自体は汎用のまま保つ）:

| 目的 | 方法 |
|---|---|
| プロジェクト固有の制約をsorter/workerに伝える | `args.context` にCLAUDE.mdの要点や触ってはいけない範囲を書く |
| 並列度を絞る/広げる | `args.maxWorkers` |
| 差し戻し許容回数を変える | `args.maxRetries` |
| モデルの世代を変える | `scripts/workflow.js` 内の `model: 'haiku' / 'sonnet' / 'opus'` を必要なら具体的なモデルID（例 `claude-haiku-4-5-20251001`）に置き換える |

汎用スキルなので、プロジェクト固有の値をこの SKILL.md や `workflow.js` に直接書き込まない。プロジェクトごとの差はすべて `args` で渡す。
